# 可用状态配方（2026-09-27 验证）

> 这份文件记录「游戏能正常进入」时的**确切环境**。任何改动之后如果又进不去，
> 照这份清单逐项对照即可。由 `python verify_working_state.py` 可自动核对。

## 一、一句话总结

**Mods 里放玩家的原始 Mod（不经控制器 staging）；XXMI 与 DLSS5 底座都放在短路径；
控制器只负责「写注入库 + 拉起 XXMI + 自检」，不碰 Mods，也不往游戏目录写运行库。**

## 三、必须避开的坑（都实际踩过）

1. **`selected_mods` 为空时，绝不能调用 `stage_and_prepare`**
   `resolve_active_set` 里「空列表 = 全部激活」。历史上因为这条，控制器每次启动都会
   把 Mods 重建成全部 20+ 个 Mod，表现为「手动启动能进、用控制器就崩」。
   现在 `stage_and_prepare` 已在源头保护：显式空列表 = 什么都不选（需 `all_when_empty=True` 才全部）。
2. **自检不能覆盖用户/游戏目录里已有的文件**
   `initialize._check_game_libs` 曾把"大小不符"当成"需要补齐"，于是每次启动都把
   原版 nvngx 换成新版 → 崩。现在已改为「已存在就不动，只在缺失时补齐」。
3. **不要手动往 Mods 里塞 Mod**
   Mods 是控制器的 staging 地盘；混着放会和 staging 产物形成同角色成对 → 崩。
4. **改配置前先关掉正在运行的控制器**
   运行中的实例会把内存里的旧配置写回磁盘，把外部修改覆盖掉。
5. **别把 XXMI / ReShade 复制进 `runtime\` 深层目录**
   3DMigoto/EFMI 对自身路径长度有硬限制，junction 也救不了（进程拿到的仍是长路径）。

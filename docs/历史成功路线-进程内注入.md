## 6. 程序源码与重新编译

两个自研件都在仓库里（不是丢失的二进制，可重建）：

| 源码 | 说明 | 构建命令（本机已有 mingw64 gcc） |
|---|---|---|
| `scripts\migoto_multi_loader.c`（568 行） | 注入器：轮询 `Endfield.exe` → 按 `inject_order.txt` 注入；`mc_bootstrap.dll` 单行时进入 *bootstrap mode*（立即注入 + 最多 20 次重试）；否则先等目标进程加载 `d3d11.dll`+`dxgi.dll`（≤45s）再注入；启动时轮换 `d3d11_log.txt` → `.prev.txt`；日志写 `<dir>\loader_debug.log` | `x86_64-w64-mingw32-gcc -O2 -municode -o migoto_loader2.exe scripts\migoto_multi_loader.c -lpsapi` |
| `scripts\mc_bootstrap.c`（76 行） | 进程内桥：等 `dxgi.dll` 出现（2ms 轮询 / 120s 超时）→ `LoadLibraryExA("<dir>\d3d11.dll", LOAD_WITH_ALTERED_SEARCH_PATH)`；日志写 `<dir>\mc_bootstrap.log` | `x86_64-w64-mingw32-gcc -O2 -shared -o mc_bootstrap.dll scripts\mc_bootstrap.c` |

关键实现点（源码原文注释）：

- 为什么要在进程内二次加载，而不是直接把 `d3d11.dll` 注入进去？
  *早期注入* 会 HookD3D11 失败；*晚期注入*（等模块就绪后再 `VirtualAllocEx`/`CreateRemoteThread`）会被反作弊拒绝。
  桥方案把"写进程内存"这一步放在进程**刚创建、还没上反作弊**的时间窗里完成。
- 注入器 `bootstrap mode` 的 20 次 × 50ms 重试，是为了对齐游戏多进程（启动器会先拉起一个壳进程，真正的渲染进程在后面）。

## 9. 复现时的坑

1. **必须 DirectX 11 启动**：D3D12 下 EFMI 的 d3d11.dll 根本不参与渲染，日志再漂亮也不出服装。
2. **管理员权限**：`d3dx.ini` 里 `require_admin = true`；注入器要能 `OpenProcess`/`VirtualAllocEx` 目标进程。
3. **Mods 目录一换，`d3dx_user.ini` 里的旧变量名就失配**（键名带 `\mods\<文件夹名>\...`）。
   从 `EFMI\Mods` 复制回去时保持同名，旧的换装状态才能继续用。
4. **别和官方 XXMI 同时注入**：两条链路同时存在会重复 Hook（历史上出现过
   `Hooking Quirk: Unexpected call back into D3D11CreateDevice`）。复现历史路线时先关掉 XXMI。
5. **游戏是多进程**：启动器会先起壳进程，注入器可能先命中的不是渲染进程；`bootstrap mode` 的
   重试就是为这个准备的，看到 `injected` 里混着失败的 pid 属正常。
6. **游戏目录里不要留代理 DLL**：`d3dcompiler_47.dll` / `vulkan-1.dll` 被第三方加载器顶替过，
   会额外注入 `plugin\*.dll`，污染判断（控制器「启动页 → 检查游戏目录注入」可查）。
7. **变体 A 的 ReShade 需成对配置**：`ReShade64.dll` 要放进 `runtime\migoto\`（loader 注入的是这个路径），
   而游戏目录里的 ReShade 代理（`d3d12.dll` / `dxgi.dll`）要保持禁用状态。
